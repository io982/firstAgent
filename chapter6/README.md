# 📚 Глава 6. RAG по документам проекта

## Проблема

В Главе 5 агент научился запоминать **факты о пользователе** (имя, название проекта). Но он по-прежнему **не понимает код проекта**:

| Вопрос пользователя | Что может агент Главы 5 |
|---|---|
| «Как меня зовут?» | ✅ Ответит из памяти |
| «Где реализован калькулятор?» | ❌ Не знает, нужно читать файлы |
| «Какие инструменты в Главе 5?» | ❌ Не знает структуру проекта |
| «Что делает функция chunk_text?» | ❌ Не может найти и объяснить |

Чтобы ответить на такие вопросы, агенту пришлось бы вручную читать каждый файл через `read_file` — долго и неэффективно.

**Цель Главы 6:** дать агенту **знание о кодовой базе** через индексацию всех файлов проекта в векторную базу.

## Решение: RAG по проекту

```text
Пользователь: "Проиндексируй мой проект"
    ↓
[index_project] → обход файлов → чанкинг → эмбеддинги → ChromaDB
    ↓
Пользователь: "Где реализован калькулятор?"
    ↓
[ask_project] → эмбеддинг запроса → поиск похожих чанков
    ↓
Найдено: chapter1/agent.py → 27: def calculator(expression)...
    ↓
Агент отвечает, указывая файл и номер строки
```

Это продолжение Главы 5: та же векторная база ChromaDB и те же эмбеддинги, но **отдельная коллекция** `project_files` для файлов проекта.

## Структура главы

## Как это работает

### 1. Чанкинг — разбиение файлов на фрагменты

Файлы проекта большие (тысячи символов), а эмбеддинги плохо работают с длинными текстами. Поэтому каждый файл разбивается на **чанки**:

```text
Файл agent.py (20000 символов)
    ↓ chunk_text_with_lines()
chunk0: строки 1–45      (эмбеддинг + текст с номерами)
chunk1: строки 43–88     (перекрытие 3 строки)
chunk2: строки 86–130
...
```

| Параметр | Значение | Зачем |
|---|---|---|
| `CHUNK_SIZE` | 1000 символов | Оптимальный размер для эмбеддинга |
| `overlap_lines` | 3 строки | Контекст на границах не теряется |
| `MIN_CHUNK_LENGTH` | 20 символов | Короткие чанки не несут смысла |

**Ключевая идея:** функция `chunk_text_with_lines` возвращает **пару** для каждого чанка:

```python
(clean_chunk, numbered_chunk)
#  clean_chunk    → для эмбеддинга (точный поиск)
#  numbered_chunk → для возврата модели (видны номера строк)
```

### 2. Эмбеддинги с префиксами nomic-embed-text ⭐

Модель `nomic-embed-text` **спроектирована работать с префиксами**. Без них качество поиска существенно ниже:

```python
# При индексации документа:
"search_document: def calculator(expression): ..."

# При поисковом запросе:
"search_query: где реализован калькулятор"
```

Это **самое важное открытие** Главы 6 — именно добавление префиксов резко улучшило поиск.

### 3. Эмбеддинг от чистого кода

Номера строк нужны модели, но **не должны попадать в эмбеддинг** — они размывают смысл кода:

```python
embeddings.append(get_document_embedding(clean_chunk))   # чистый код → поиск
documents.append(numbered_chunk)                          # с номерами → возврат
```

ChromaDB позволяет хранить эмбеддинг и текст отдельно, чем мы и пользуемся.

### 4. Отдельная коллекция и детерминированные ID

| Аспект | Реализация |
|---|---|
| Коллекция | `project_files` (отдельно от `agent_memory` Главы 5) |
| ID чанка | `{путь_к_файлу}::chunk{N}` — детерминированный |
| Переиндексация | `clear_project_index()` удаляет старое, создаёт новое |

Детерминированные ID делают переиндексацию **идемпотентной**: чанк перезаписывается, а не дублируется.

## Инструменты Главы 6

### index_project — проиндексировать проект

```python
@chapter4_tools.tool("index_project", "индексирует все файлы проекта...")
def index_project_tool(path: str = ".") -> str:
```

Что делает:
1. Очищает старый индекс (`clear_project_index`)
2. Рекурсивно обходит директорию, пропуская `SKIP_DIRS`
3. Фильтрует файлы по `INDEX_EXTENSIONS`
4. Разбивает каждый файл на чанки, считает эмбеддинги, сохраняет

```text
INDEX_EXTENSIONS = {".py", ".md", ".txt", ".json", ".yml", ".yaml", ".toml", ".rst"}
SKIP_DIRS = {".git", "__pycache__", "node_modules", ".venv", "venv", "chroma_db", ...}
```

### ask_project — спросить о проекте

```python
@chapter4_tools.tool("ask_project", "ищет информацию в коде и документах проекта...")
def ask_project(query: str, max_results: int = 5) -> str:
```

Ищет релевантные чанки и возвращает их с указанием файла. Если индекс пуст — подсказывает использовать `index_project`.

### project_stats — статистика индекса

```python
@chapter4_tools.tool("project_stats", "показывает статистику индекса проекта...")
def project_stats_tool() -> str:
```

Возвращает количество проиндексированных файлов и чанков.

## ⚠️ Особенности поиска по коду

Поиск по коду через текстовые эмбеддинги **не идеален**, и это важно понимать:

1. **`nomic-embed-text` обучен на естественном языке, не на коде.** Запрос «где реализован калькулятор» может находить упоминания в документации лучше, чем `def calculator`.

2. **README.md содержит много упоминаний** и часто попадает в топ вместо реальной реализации. В промпте есть правило «различай упоминание и реализацию», но это не гарантирует 100% точности.

3. **Модель может галлюцинировать** — выдумывать номера строк или несуществующие функции. Поэтому в промпте жёсткие правила: «используй ТОЛЬКО номера строк из фрагментов», «не отвечай без вызова ask_project».

### Диагностика через test_search.py

Чтобы проверить качество поиска **напрямую**, без модели:

```bash
python -m chapter6.test_search
```

Скрипт покажет, какие чанки находятся по разным запросам и их `distance`:
- `distance < 0.2` — высокая релевантность
- `distance 0.3–0.5` — низкая релевантность (поиск неточный)

Это главный инструмент отладки RAG.
