# 🔌 Глава 8. Нативные tool_calls

> **Статус: каркас.** Файлы созданы, функции описаны, реализации нет —
> каждая заглушка бросает `NotImplementedError`. Этот README фиксирует
> замысел и данные, на которых он построен.

## Долг, который закрывает глава

В разделе 1.5 курс сознательно выбрал текстовый парсинг: модель возвращает
JSON-вызов обычным текстом, а ядро вылавливает его регулярками и
`json.JSONDecoder`. Причина была практическая — так работает любая модель,
включая собранные из GGUF вручную.

У Ollama есть и второй путь: передать в запросе поле `tools`, и получить
структурированное `message.tool_calls`. Там нечего парсить и нечего сломать
пересказом.

## Что показал замер (20 августа 2026)

Прежде чем писать главу, отправили запрос с `tools` каждой модели курса:

| Модель | `ollama show` | `tool_calls` | `content` |
|---|---|---|---|
| `qwen2_5coder3b_q5` | tools заявлен | пусто | рассуждение и XML-блок `<tools>` |
| `qwen2.5-coder:7b` | tools заявлен | пусто | `{"name": "calculator", ...}` |
| `llama3.1:8b` | tools заявлен | **заполнено** | **пусто** |

Из этой таблицы следуют три вывода, и все три меняют замысел главы.

**Флаг `tools` ничего не гарантирует.** Все три модели его объявляют,
работает он у одной. Значит определять формат надо запросом, а не чтением
`ollama show`.

**Переходить целиком некуда.** Для двух моделей курса из трёх нативного
формата просто нет. Глава не может называться «переходим на tools API» —
агент обязан уметь оба пути.

**Наивное включение `tools` ломает агента.** У `llama3.1:8b` при заполненном
`tool_calls` поле `content` пустое. Ядро Главы 1 не найдёт в пустой строке
вызова, решит, что это финальный ответ, и вернёт пользователю пустоту.
Причём именно на той модели, которая формат поддерживает.

## Структура главы

```text
chapter8/
├── agent.py           Точка входа: определяет формат при старте, потом REPL
├── test_formats.py    Прогон по моделям: кто отдаёт tool_calls, кто нет
└── src/
    ├── schema.py      TOOL_REGISTRY → JSON Schema для поля tools
    ├── probe.py       Определение формата пробным запросом
    └── native.py      Ядро, умеющее оба формата
```

### `src/schema.py`

Реестр Главы 4 уже хранит параметры каждого инструмента — их извлекает
`_extract_parameters` через `inspect.signature`. Здесь эти же данные
перекладываются в JSON Schema. Ничего нового собирать не нужно, и это
хороший повод показать, что решение Главы 4 окупилось второй раз.

### `src/probe.py`

Один короткий запрос с заведомо подходящим инструментом — и смотрим, куда
попал вызов: в `tool_calls`, в `content` или никуда. Три исхода описаны
константами `FORMAT_NATIVE`, `FORMAT_TEXT`, `FORMAT_UNKNOWN`.

### `src/native.py`

Цикл ReAct Главы 1 с двумя отличиями:

- разбор ответа: сначала `tool_calls`, при пустом поле — текстовый парсер
  Главы 1;
- пустой ответ без вызова инструмента считается сбоем, а не финальным
  ответом пользователю.

Отдельный вопрос, который предстоит решить: при нативном формате результат
инструмента положено возвращать сообщением с ролью `tool`, а курс до сих
пор подставлял его как `user` с префиксом `Observation from`. Оба варианта
придётся поддержать.

### `test_formats.py`

То же, чем `test_hybrid.py` стал для Главы 7: файл, который превращает
утверждение главы в проверяемый факт. В нём записаны ожидаемые форматы
для трёх моделей — расхождение будет видно сразу, если Ollama или модель
изменят поведение.

## Что читатель должен унести

Что «function calling» — не свойство модели, а договорённость между
моделью, шаблоном промпта и сервером. Любое звено может её не поддержать,
и проверяется это запросом, а не документацией.

И более общее: агент, рассчитанный на один формат ответа, ломается при
смене модели. Поддержка двух путей выглядит избыточной ровно до первого
такого случая.
