# 🔌 Глава 8. Нативные tool_calls

Глава написана и работает. Всё, что ниже, проверено на трёх моделях:
`qwen2_5coder3b_q5`, `qwen2.5-coder:7b`, `llama3.1:8b`.

## Долг, который закрывает глава

В разделе 1.5 курс сознательно выбрал текстовый парсинг: модель возвращает
JSON-вызов обычным текстом, а ядро вылавливает его регулярками и
`json.JSONDecoder`. Причина была практическая — так работает любая модель,
включая собранные из GGUF вручную.

У Ollama есть и второй путь: передать в запросе поле `tools`, и получить
структурированное `message.tool_calls`. Там нечего парсить и нечего сломать
пересказом.

## Что показал замер (20 августа 2026)

Прежде чем писать главу, отправили запрос с `tools` каждой модели курса:

| Модель | `ollama show` | `tool_calls` | `content` |
|---|---|---|---|
| `qwen2_5coder3b_q5` | tools заявлен | пусто | рассуждение и XML-блок `<tools>` |
| `qwen2.5-coder:7b` | tools заявлен | пусто | `{"name": "calculator", ...}` |
| `llama3.1:8b` | tools заявлен | **заполнено** | **пусто** |

Из этой таблицы следуют три вывода, и все три меняют замысел главы.

**Флаг `tools` ничего не гарантирует.** Все три модели его объявляют,
работает он у одной. Значит определять формат надо запросом, а не чтением
`ollama show`.

**Переходить целиком некуда.** Для двух моделей курса из трёх нативного
формата просто нет. Глава не может называться «переходим на tools API» —
агент обязан уметь оба пути.

**Наивное включение `tools` ломает агента.** У `llama3.1:8b` при заполненном
`tool_calls` поле `content` пустое. Ядро Главы 1 не найдёт в пустой строке
вызова, решит, что это финальный ответ, и вернёт пользователю пустоту.
Причём именно на той модели, которая формат поддерживает.

### `src/schema.py` — реестр Главы 4 окупается второй раз

Параметры инструментов уже лежат в реестре: их извлекает
`_extract_parameters` через `inspect.signature`. Здесь они перекладываются
в JSON Schema — собирать заново нечего.

Одна тонкость всплыла сразу. `_extract_parameters` перечисляет **всё**, что
видит в сигнатуре, включая `**kwargs` у инструмента `remember`. Для промпта
это безвредно, а в JSON Schema превратилось бы в обязательное поле с именем
`kwargs`, которое модель начнёт заполнять чем попало. Поэтому при сборке
схемы параметры вида `VAR_KEYWORD` отбрасываются:

```python
def _skipped_parameters(func) -> set:
    return {name for name, p in inspect.signature(func).parameters.items()
            if p.kind in (p.VAR_KEYWORD, p.VAR_POSITIONAL)}
```

### `src/probe.py` — формат выясняется запросом

Один короткий запрос с пробным инструментом — и смотрим, куда попал вызов:
в `tool_calls`, в `content` или никуда. Стоит пары секунд и снимает целый
класс загадочных поломок.

Пробный инструмент `probe_add` намеренно не из реестра: проба должна
работать до того, как агент к чему-либо подключился. По той же причине
ответ разбирается своей функцией, а не парсером Главы 1 — тот сверяется
с `KNOWN_TOOLS`.

### `src/native.py` — ядро на два протокола

Отличий от Главы 1 три:

| | Текстовый формат | Нативный формат |
|---|---|---|
| Запрос | как раньше | плюс поле `tools` |
| Вызов приходит | в `content` текстом | в `message.tool_calls` |
| Результат уходит | `role: user`, «Observation from …» | `role: tool` |

Плюс защита, ради которой глава и написана: **пустой ответ без вызова
инструмента считается сбоем, а не финальным ответом**. Без неё агент
на нативной модели молча возвращает пользователю пустую строку.

## Два открытия, которых не было в плане

### Формат сообщения с результатом оказался ни при чём

Первая рабочая версия вызывала инструмент дважды подряд с одинаковыми
аргументами:

```text
Итерация 1: [Agent] Вызываю calculator {'expression': '(15 * 7) + 3'} → 108
Итерация 2: [Agent] Вызываю calculator {'expression': '(15 * 7) + 3'} → 108
Итерация 3: Результат: 108.
```

Для калькулятора это лишняя итерация, для `write_file` — файл, записанный
дважды. Естественная гипотеза: неправильно возвращаем результат. Проверили
три варианта сообщения — `role: tool` с именем инструмента, без имени,
и вовсе без `tool_calls` в истории ассистента. **Ни один не давал повтора.**
Значит дело не в этом.

### Причина была в системном промпте

Промпт Главы 4 объясняет модели, как выводить вызов текстом:

```text
1. Если нужен инструмент, ответь ТОЛЬКО JSON-вызовом.
```

При нативном формате это второй протокол поверх первого. Модель делает обе
вещи сразу: вызывает инструмент структурой, а следом повторяет вызов,
потому что промпт просил JSON. Лечится тем, что при нативном формате
берётся другой промпт — без инструкций по JSON и без перечисления
инструментов, которые и так уходят в поле `tools`:

```python
def system_prompt_for(tool_format: str) -> str:
    if tool_format != FORMAT_NATIVE:
        return base.SYSTEM_PROMPT
    return NATIVE_SYSTEM_PROMPT
```

После замены — один вызов вместо двух, и ответ на четыре секунды быстрее.

**Вывод, который стоит запомнить:** системный промпт — часть протокола.
Смешение двух протоколов не ломает агента заметно, оно делает его вдвое
расточительнее, и заметить это можно только в подробном режиме.

Один и тот же агент, один и тот же реестр инструментов, разные протоколы —
и пользователь разницы не замечает.

## Что читатель должен унести

Что «function calling» — не свойство модели, а договорённость между
моделью, шаблоном промпта и сервером. Любое звено может её не поддержать,
и проверяется это запросом, а не документацией.

И более общее: агент, рассчитанный на один формат ответа, ломается при
смене модели. Поддержка двух путей выглядит избыточной ровно до первого
такого случая.
