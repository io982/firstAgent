# 🔍 Глава 7. Гибридный поиск: ключевые слова + векторы

## Проблема

Глава 6 научила агента искать по коду проекта эмбеддингами. Работает — но
измерение показывает, где именно не работает:

```text
Запрос: 'def calculator'
  📄 [README.md]              (distance=0.382)
  📄 [chapter4/src/tools.py]  (distance=0.391)
  📄 [chapter6/agent.py]      (distance=0.402)
```

Реализация `calculator` в `chapter1/agent.py` в топ-3 не попала, а все
расстояния лежат в диапазоне 0.3–0.4, который сама Глава 6 называет
«поиску верить нельзя».

Причина в модели эмбеддингов. `nomic-embed-text` обучен на естественном
языке: он хорошо ловит смысл фразы «где считается арифметика» и плохо —
точный идентификатор `def calculator`. Для эмбеддинга `calculator`,
`calculate` и `вычислитель` почти одно и то же, а для программиста,
который ищет конкретную функцию, — совсем нет.

**Цель Главы 7:** добавить второй способ поиска, который силён ровно там,
где слаб первый, и — обязательно — измерить, стало ли лучше.

## Два поиска, разные сильные стороны

| | Векторный поиск | BM25 (ключевые слова) |
|---|---|---|
| Что сравнивает | Смысл | Совпадение слов |
| «где считается арифметика» | ✅ находит | ❌ таких слов в коде нет |
| `def calculator` | ⚠️ размывает | ✅ точное совпадение |
| Опечатка в запросе | ✅ переживёт | ❌ не найдёт |
| Редкий идентификатор | ⚠️ теряется | ✅ высокий IDF |

Ни один из них не лучше другого — они ошибаются в разных местах. Отсюда
идея: искать обоими и объединять результаты.

## Что такое BM25

Код: → [chapter7/src/bm25.py](chapter7/src/bm25.py)

BM25 (Best Matching 25) — классика поиска по ключевым словам, которой
десятки лет. Идея в трёх частях:

| Составляющая | Смысл |
|---|---|
| **TF** (term frequency) | Чем чаще слово в документе, тем документ релевантнее |
| **IDF** (inverse document frequency) | Редкое слово важнее частого: `calculator` информативнее, чем `def` |
| Нормализация по длине | В длинном документе слово встречается «случайно» чаще, поэтому длину учитываем |

Именно IDF решает главную проблему: в этом проекте слово `def` встречается
почти в каждом фрагменте и потому почти ничего не значит, а `calculator` —
в единицах, и его совпадение весит много.

Токенизация у нас чуть отличается от обычной текстовой — код требует
сохранять пунктуацию как отдельные токены:

```python
tokens = re.findall(r'\w+|[^\w\s]', text.lower())
```

Токены каждого документа считаются один раз при построении индекса. Если
делать это в момент запроса, каждый поиск заново разбирает весь индекс
на слова: на 250 фрагментах заметно, на 10 000 — неприемлемо.

## Как объединить два списка: Reciprocal Rank Fusion

Первое, что приходит в голову, — сложить оценки с весами:

```python
score = 0.5 * vector_score + 0.5 * bm25_score      # так делать не надо
```

Здесь две ловушки, и обе неочевидные.

**Шкалы несопоставимы.** Векторный score — это `1 − косинусное расстояние`,
величина абсолютная. BM25 выдаёт неограниченное число, зависящее от размера
коллекции и редкости слов. Складывать их — всё равно что складывать
градусы с километрами. Нормализация по максимуму внутри выдачи не спасает:
топ-1 любого списка тогда всегда равен 1.0, независимо от того, хорош он
или это лучшее из плохого.

**Отсутствие в списке считается нулём.** Документ, который нашёл только
BM25, получает `vector_score = 0.0` — и штрафуется так, будто векторный
поиск активно его отверг. Хотя на деле он просто не попал в топ-N выдачи.

**Reciprocal Rank Fusion** обходит обе ловушки, потому что складывает
не оценки, а места:

```python
score(документ) = Σ  1 / (k + место_в_списке)
```

Сумма берётся по тем спискам, где документ вообще есть. Оценки не
участвуют — значит, приводить шкалы друг к другу не нужно. Документ,
найденный обоими способами, получает два слагаемых и обгоняет тех, кто
нашёлся одним, — а это ровно тот сигнал, который нам нужен.

Константа `k = 60` — из статьи, где RRF был предложен. Она задаёт, насколько
резко первые места отрываются от остальных: чем меньше `k`, тем острее
разрыв. Менять её без замера незачем.

## Замер: стало ли лучше

Код: → [chapter7/test_hybrid.py](chapter7/test_hybrid.py)

```bash
python -m chapter7.test_hybrid
```

Это главный файл главы. Без него утверждение «гибридный поиск лучше»
остаётся верой.

Устроен он как набор пар «запрос → файл, который считается правильным
ответом». Правильных файлов может быть несколько: `calculator`, например,
определён и в Главе 1, и в реестре плагинов Главы 4.

```python
CASES = [
    ("def calculator", {"chapter1/agent.py", "chapter4/src/tools.py"}),
    ("автозапуск сервера ollama", {"chapter1/agent.py"}),
    ("idf inverse document frequency", {"chapter7/src/bm25.py"}),
    ...
]
```

Метрики две:

| Метрика | Что показывает |
|---|---|
| **hit@3** | В какой доле запросов нужный файл попал в первые три результата |
| **MRR** | Насколько высоко он там стоял: первое место даёт 1.0, второе 0.5, третье 0.33 |

Один и тот же набор прогоняется в трёх режимах — `vector`, `bm25`,
`hybrid`, — и это единственный способ честно ответить на вопрос
«а нужен ли вообще второй поиск».

## Результат замера: гибрид проиграл

Первый прогон дал не тот результат, которого ждали:

| Режим | hit@3 | MRR |
|---|---|---|
| только векторы | 33% | 0.18 |
| только BM25 | **50%** | 0.29 |
| гибрид (RRF) | 44% | 0.21 |

Чистый BM25 обошёл гибрид. Без замера глава закончилась бы фразой
«мы добавили BM25, стало лучше» — и это было бы неправдой.

## Две ловушки корпуса, обе видны в списке промахов

`test_hybrid.py` печатает не только числа, но и то, что вернулось вместо
правильного ответа. Там всё и нашлось.

**Ловушка первая: документация цитирует код.**

```text
'где реализован калькулятор'
   вернул: README.md, chapter6/README.md, chapter6/README.md
```

README этого проекта — две тысячи строк с листингами всех глав. Поиск
честно возвращает README: там действительно есть `def calculator`. Только
пользователю нужен `.py`-файл. Векторный поиск тянет документацию особенно
охотно: связный русский текст ближе к русскому запросу, чем код
на английском.

**Ловушка вторая: агенты хранят примеры прямо в коде.**

```python
# внутри chapter6/agent.py, в строке PROJECT_RULES:
User: Observation from ask_project: 1. [chapter1/agent.py]
27: def calculator(expression: str) -> str:
```

Это не код — это few-shot пример внутри промпта. Но для поиска он выглядит
как идеальный ответ: нужное имя, нужный путь, номер строки. Модель, получив
такой фрагмент первым, отвечает уверенно и неверно — номер строки в примере
выдуман изначально.

## Две ручки, обе обоснованы замером

```python
DOC_EXTENSIONS = {".md", ".rst", ".txt"}
DOC_DEMOTION = 0.3

PROMPT_EXAMPLE_DEMOTION = 0.3      # фрагмент с "Observation from" рядом с репликой диалога
```

| Что добавили | hit@3 | MRR |
|---|---|---|
| гибрид RRF без штрафов | 44% | 0.21 |
| + понижение документации | 78% | 0.55 |
| + понижение примеров промпта | **89%** | 0.62 |

Маркер примера намеренно узкий: «Observation from» рядом с «User:»
или «Assistant:». Так помечаются 4% фрагментов — ровно блоки промптов.
Для сравнения, первая версия главы искала слова «пример» и «example»
и помечала 19% фрагментов, включая настоящие реализации `index_file`
и `current_time`.

Перед тем как оставить штраф документации, проверили устойчивость — что
будет, если крутить его вместе с весом BM25:

| штраф документации | вес BM25 ×1 | ×2 | ×3 |
|---|---|---|---|
| 1.0 (нет штрафа) | 47% | 41% | 29% |
| 0.7 | 47% | 71% | 76% |
| 0.5 | 71% | 82% | 82% |
| 0.3 | **82%** | 82% | 82% |

Читается так: результат определяет штраф, а не вес BM25 — при 0.3 любой вес
даёт одно и то же. Значит вторая ручка не нужна, веса остаются равными.
(Таблица снята на первых 17 запросах, до добавления восемнадцатого.)

И то, и другое — **понижение, а не исключение**: иногда ответ действительно
в документации, и тогда она должна находиться, просто последней.

## Итог: поиск починен, ответы — нет

С обеими поправками:

| Режим | hit@3 | MRR |
|---|---|---|
| только векторы | 56% | 0.49 |
| только BM25 | 83% | 0.61 |
| гибрид (RRF) | **89%** | 0.62 |

Гибрид наконец обгоняет обе половины по отдельности — но заслуга тут
не столько слияния, сколько работы с корпусом.

**Чего глава не решает.** Хороший поиск не делает ответ правильным.
Лучше всего это видно по двум соседним вопросам в одной сессии на 3B.

Вопрос первый — ответ верный, все номера строк настоящие:

```text
Вы > где реализовано чтение файлов?
🤖 Агент > Чтение файлов реализовано в следующих файлах:

1. **chapter1/agent.py**:
   - Функция `read_file` на строках 308-319.
   - Функция `list_directory` на строках 283-294.

2. **chapter4/src/tools.py**:
   - Функция `read_file` на строках 186-195.
   - Функция `list_directory` на строках 172-176.
```

Проверено по файлам: 308, 283, 186, 172 — на момент прогона всё совпадало
(позже в chapter1/agent.py добавились докстринги, и номера сдвинулись —
транскрипт остаётся записью прогона). Модель скопировала
номера из Observation, как и просили.

Вопрос второй, следующий в той же сессии — ответ неверный:

```text
Вы > где реализован калькулятор?
🤖 Агент > Калькулятор реализован в chapter4/src/tools.py:
           30: def calculator(expression: str) -> float:
```

Файл верный — его нашёл поиск. Дальше всё выдумано: `def calculator`
находится на строке 165, сигнатура `-> str`, а на строке 30 лежит совсем
другая функция. Строки `-> float` нет нигде в проекте.

**Вывод не «модель всегда врёт», а хуже — «врёт непредсказуемо».** Один
и тот же агент, один и тот же индекс, соседние вопросы: там скопировал,
здесь сочинил. Отличить по виду ответа нельзя — оба выглядят одинаково
уверенно.

Тот же прогон показал третью беду, уже не с номерами:

```text
Вы > где определен инструмент агента калькулятор?
🤖 Агент > [вызывает calculator с выражением "2+2"] Калькулятор вернул 4.
```

На слово «калькулятор» модель выбрала сам калькулятор вместо поиска
по проекту. До `ask_project` дело не дошло — это ошибка выбора инструмента.

А иногда в финальный ответ утекают сырые фрагменты Observation вместе
с пометками «[фрагмент обрезан]» и номерами найденных мест: модель
пересказывает не результат, а выдачу инструмента.

Ни одно из трёх поиском не лечится. Это задачи следующих глав: нативные
`tool_calls` вместо парсинга JSON (выбор инструмента), критик, сверяющий
ответ с Observation (выдуманные номера и утечка выдачи). Пока их нет,
правило такое: **на 3B файлу верить можно, номеру строки — только после
проверки.**

## Проверка теории: помогает ли модель побольше

Раз ответы портит модель, логично спросить — а если взять другую?
Проверили три на одной машине (GTX 1660 SUPER, 6 ГБ) и одном индексе:
эмбеддинги считает `nomic-embed-text`, качество поиска от основной модели
не зависит вообще.

**Вопрос, на котором 3B выдумала всё:**

```text
Вы > где реализован калькулятор?

3B (Q5)      > 30: def calculator(expression: str) -> float:
               ← ни строки, ни сигнатуры в проекте не существует

7B coder     > def calculator(expression: str) -> str:   ← код верный, номера нет
               ...а также в ci_smoke.py и chapter6/test_search.py
               ← там вызовы в тестах, а не реализация

llama3.1:8b  > chapter4/src/tools.py на строке 165:
               def calculator(expression: str) -> str:   ← верно и то, и другое
```

3B пересказывает по памяти, 7B-coder копирует код, но теряет номера
и путает упоминание с реализацией, llama3.1 даёт ровно то, что спрашивали.

**Вопрос-контроль «где реализовано чтение файлов»** прошли все три:
`chapter1/agent.py:308` и `chapter4/src/tools.py:186` названы верно
(номера — на момент прогона).
Формулировка однозначная, в выдаче лежит именно то, что нужно.

**Вопрос, который провалили все три:**

```text
Вы > где определен инструмент агента калькулятор?

3B           > [вызывает calculator: 2+2] Калькулятор вернул 4.
7B coder     > Инструмент агента калькулятор не определен.  ← поиск не вызывался
llama3.1:8b  > [вызывает calculator: 2+2] 2 + 2 = 4
```

Ни одна не сходила в `ask_project`, хотя файл в индексе есть и по метрике
находится в топ-3. Слово «калькулятор» перевешивает вопрос «где определён».
Размер модели тут не помогает.

**Цена вопроса:**

| | 3B coder (Q5) | 7B coder (Q4) | llama3.1:8b (Q4) |
|---|---|---|---|
| Размер в памяти | 2.4 ГБ | 5.4 ГБ | 6.2 ГБ |
| Размещение на 6 ГБ | 100% GPU | 79/21 GPU/CPU | 68/32 GPU/CPU |
| Скорость | 73 ток/с | 24 ток/с | 16 ток/с |
| Ответ с инструментом | 10–20 с | 30–45 с | ~14 с |
| Выдумывает детали | да | нет | нет |
| Нативные `tool_calls` | нет | нет | да |

llama3.1 самая медленная по токенам и самая быстрая по ответу: она отвечает
коротко, а 7B-coder разворачивает простыню с листингами.

**Итог:** для ответов по коду — llama3.1:8b. Выдумывание лечится сменой
модели, выбор инструмента — нет.
